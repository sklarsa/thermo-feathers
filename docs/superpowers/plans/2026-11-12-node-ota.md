# Node updates over ESP-NOW (milestone 5)

Design: [the spec's firmware updates section](../specs/2026-11-10-espnow-gateway-design.md#firmware-updates-for-nodes).

## Settled on the bench, 2026-11-12

- espflash's bootloader doesn't roll back: a node booted a panicking image in `ota_1` forever.
- ESP-IDF v5.5.1's bootloader with `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` does: the same image
  ran once, and the next wake was the old image again.
- A pending image has to confirm itself in its first boot: a deep-sleep wake goes through the
  bootloader, which abandons a slot still pending.
- An image's own SHA-256 is its last 32 bytes, and its app description (magic `0xABCD5432`,
  version, project name) starts at byte 32.

## Choices

- **Build ID:** a node reports `fw` as `<version>-<6 hex>`, the hex from its image's own SHA-256.
  Every build differs, so the gateway knows an update took by the `fw` the node reports next.
- **Node or gateway image:** the node's app description names the project `thermo-node`, the
  gateway's `thermo-gateway`. Gateway and node both refuse an image that isn't `thermo-node`.
- **Transfer:** the node pulls. `Fetch { offset }` gets `Chunk { sha, total, offset, data }` with
  128 bytes, so 32 chunks fill a flash sector. Every chunk carries the whole image's SHA-256, so a
  node notices an image replaced mid-transfer and stops.
- **Node:** after an exchange whose reply has the update flag, if charging, at 40 % or more, or
  without a gauge: write the other slot a sector at a time, check SHA-256 and the app description,
  point `otadata` at it as `New`, reset. The new image marks itself `Valid` after its first acked
  send. Anything else rolls back.
- **Gateway:** `POST /update?to=all|id,id` with the raw `.bin` as the body (the page's form sends
  it with a few lines of JavaScript; `scripts/ota.sh` with curl). The image sits in PSRAM, checked
  on arrival. Each target goes waiting → sending → sent → done, or failed if it comes back on its
  old build. Done and failed nodes aren't offered it again.
- **Bootloader:** `bootloader/` holds the build inputs, a `build.sh` for the pinned ESP-IDF image,
  and the built `.bin`. `scripts/flash-node.sh` flashes it. Each node needs one USB flash with it.

## Steps

1. `bootloader/`, and `flash-node.sh` passes `--bootloader`.
2. Library, host-tested: `Fetch`/`Chunk` frames, image digest and app description parsing, the
   build ID, the gateway's per-node rollout state.
3. Node: build ID at cold boot, the update, marking itself valid.
4. Gateway: upload, serving chunks, the rollout on the web page.
5. `scripts/ota.sh`: build, make the image, upload.
6. On the bench: update the node over the air; push an image that panics and watch it roll back;
   upload a gateway image and see it refused.

## Results, 2026-11-12

- An update of the 535 KB node image took about 24 s over ESP-NOW, from the node's next wake.
  Two went through and confirmed (`0.4.0-919258`, `0.4.0-ccc4e5`).
- An image that panics on its trial boot rolled back at the next wake; the gateway's page said so.
- The gateway refused its own image, random bytes, a node image with one bit flipped, a missing
  `to` and a bad node ID.

Found on the way:

- esp-bootloader-esp-idf 0.6's `find_partition` panics (`unreachable!`) on custom partition types,
  and partitions.csv has three. The node finds partitions by raw type instead.
- Its `Ota` reads otadata entries through a misaligned pointer. `src/otadata.rs` does it instead.
- The build ID has to be worked out every boot: after a rollback the old image wakes up with the
  new one's State, and reported the new build's ID until this was fixed.
- The flash window now comes before any of that, so a crash after it can still be flashed over.

## After review, 2026-11-12

- otadata: rolled-back (ABORTED, INVALID) entries no longer count as current, as in ESP-IDF's
  bootloader. Before, the update after a rollback could write over the entry the node boots by.
- A confirmed image that crashes 3 wakes in a row without reaching the gateway goes back to the
  previous one if otadata still names it valid (`otadata::fall_back`). Tested: an image that
  panics from its fourth boot went back by itself after three.
- The gateway marks a node that comes back on its old build after "done" as rolled back; a refused
  upload no longer cancels the rollout running; an LC709203F node only updates while charging; the
  update backoff is set before an attempt.
- The gateway updates itself the same way (`POST /update/gateway`, `scripts/ota.sh <addr> gateway`):
  confirmed once it has WiFi, the time and a QuestDB ack, back after 10 minutes otherwise, and the
  same three-crash fallback. Tested: an update kept through a reset, and a panicking image rolled
  back in 13 s.
